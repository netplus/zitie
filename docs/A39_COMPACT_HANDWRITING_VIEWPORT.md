# A3.9：缩小书写区，让字形、笔压与主要操作尽量同屏

- 需求与截图：[Issue #135](https://github.com/netplus/zitie/issues/135)：水（#77）的田字格几乎占满浏览器可见高度；笔顺进度、重播、上一笔／下一笔、倍速和力度图表无法一起观察、操作。
- 范围：正式 `animation/book.html`，以原 v0.5.1 PDF 的 **201 字／1045 笔**为源；不触碰正式 299 页 PDF、原 SVG 墨迹、中心线、规范笔顺、时间轴和 A3.6 显墨前缘屏障，不激活冻结的硬笔路线。

## 根因

A3.8 用 `#paperSvg{width:100%;max-width:535px;aspect-ratio:1}` 表示书写正方形。此上限只针对页面宽度，不涉及笔记本浏览器**高度**；在较矮的视口内，字格可能把进度和播放按钮推到屏幕下方。而早前为修复 1020px 画布意外缩到 302px 所建立的“至少 490px”断言，和此次明确要求**适度缩小**的设计目标也发生冲突，必须有意识地替换为新的尺寸约束，不能简单移除回归验证。

## 实现

1. 桌面/笔记本：`--board-size:clamp(250px,calc(100svh - 450px),410px)`。在 768px 高的视口下，正方形目标约 318px；在更高屏幕最多 410px。书写舞台始终在主播放器内居中，保持原始 SVG 等比缩放、不裁切字形；已有 220px 笔压栏放在右侧（包含 1020px 笔记本），避免额外增加一条完整的控件高度。列宽不足时字格还会受容器宽度限制，自然缩小。
2. ≤720px：笔压栏紧贴字格上方并保留 sticky，二者相同宽度；≤510px 的手机进一步压低高度感知尺寸（首次 300px 上限在 390×844 Chrome 实测按钮底部为 864.9px，超出 844px 屏幕约 21px，因此修正为 270px 上限），收为 `clamp(230px,calc(100svh - 505px),270px)`，主操作按钮采用三列栅格、速度按钮独立第三行。小手机优先保证完整字格、模拟力度和进度可见；极短屏幕允许次要内容自然滚动，不依靠重叠的悬浮播放控制。
3. 缩紧页面和主卡片上下留白、较大的标题与图例间距，减少“画布外”无效竖向占用。笔尖、笔画填充、PDF 链接、笔画跳转、按键语义、StyleController 和曲线绘制完全不动。未添加任何网络资产或字体资源。

## 量化验收

- 在真正的 Chromium 中加载正式 PDF-backed `book.html?id=77`，模拟笔压版定位水第二笔中段，让力度数值与曲线绘出并持续可见。
- 逐个实际设定 iframe **宽度和高度**：1440×900、1366×768、1020×768、800×900、390×844、390×667；不得只改变宽度。验证画布为 1:1，无水平溢出，无 SVG 裁切，压力面板位置正确；所有 ≥768px 高的测试视口下，播放、重播、上一笔、下一笔、本笔重播、完整字形与四档速度按钮、进度条均完整处于首屏。390×667 验证核心可观察区域，允许操作区继续滚动。
- 保持 A3.8 笔压按钮仅一份，模式与当前字／笔进度随宽高改变不丢失。回归 A3.7 两风格同墨、A3.6 1045笔／2090帧光栅前缘、A3.5 运笔A/B及正式 Book 299 页全部结构检查。
- 每轮 Chromium 记录 `paperWidth`、`paperBottom`、`controlsBottom`、`screenHeight` 等实际数值，并捕获 1366×768/390×844 模拟力度真实画面供视觉复核。无异常才合入，合并 SHA 对应 Pages 实际 Deploy 成功后才能宣布上线。

**证据边界：**“同屏”受实际浏览器工具栏、安全区、用户字体放大、系统缩放影响，不能保证每种设备都无需滚动；以上是指定 CSS 视口、浏览器和模式的确定性测试，不是对所有硬件及人体书写笔压的承诺。模拟笔压仍非实测。
